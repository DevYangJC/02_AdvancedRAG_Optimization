# 注释检查技能（comments-check）

## 三条检查规则（核心标准）

### 1. 密度检查 —— 脚本量化执行

- **目标**：注释行数 ≈ 代码行数的 **30%**（10 行中 3 行注释、7 行正文）
- 达标区间 **25%~35%**；低于 25% 判「注释不足」；高于 40% 判「注释冗余」
- **客观数据来源**：运行 `node scripts/check-comments.js [路径]`，以脚本输出为准，不靠目测
- 例外豁免：纯类型声明文件（env.d.ts）、配置类文件（vite.config.ts）不强制达标，但仍需关键处注释
- 脚本已适配本仓库技术栈：支持 `.ts/.js/.vue`（`//`、`/* */`、`<!-- -->`）与 `.py`（`#`）；自动排除 node_modules/.venv/data 等目录
- **质量优先于密度（最高原则）**：密度是参考指标，不是目的——
  - 禁止为了凑密度写多余注释：空泛注释（`# 计算`）、复述代码本身的注释（`# x = x + 1 表示把 x 加一`）、与上下文重复的注释，一律不写；写了也判为无效
  - 注释必须承载信息增量：解释「为什么这样写」「这行在业务流程里的作用」「这个分支在防什么」，代码本身能看懂的「是什么」不用注释
  - 文件密度未达标但注释质量高、无遗漏场景时：如实报告差距（缺 N 行估算），**不强行补注释**；密度超标但注释都有信息量时：**不删**（冗余判定只针对无意义注释，不是机械删行）
  - 硬性缺失（函数无头注释、核心逻辑无任何说明）仍判不通过——质量检查不看密度数字，看「该注释的地方是否注释了」

**函数/核心代码必须注释的硬性要求**（即使整体密度达标，以下场景缺注释仍判不通过）：
- 每个函数必须有函数头注释：**用途 / 参数 / 返回值**（短函数可一句概括）
- 每条重要核心代码：认证鉴权（JWT/bcrypt）、RAG 管线环节（检索/重排/改写）、数据库事务、状态流转、边界处理、并发控制（信号量/锁）

### 2. 一致性检查 —— 注释与代码匹配（语义判断）

逐条核对注释描述与代码实际行为：

- 参数名、返回值、行为描述是否**过时**（重构后未同步）
- 注释中提到的条件/步骤与代码实际逻辑是否一致
- 是否存在**复制粘贴注释**（张冠李戴：A 函数注释贴到 B 函数）
- 注释与代码矛盾时，以**代码为准**，注释视为缺陷

### 3. 小白视角检查 —— 新手可读性（语义判断）

假设读者对业务完全不熟悉，注释应能让其在 5 秒内理解该行/该函数的作用与意图：

- 解释**「为什么」**，而不只是**「是什么」**
- 关键业务约定写明背景（例：「语义缓存 key 用规范化问题 md5，保证同义问题命中」）
- 缩写/术语首次出现要解释（例：RAG、SSE、LCEL、WAL、JWT）
- 反例：`# 查询数据库` → 正例：`# 校验会话归属：非本人一律 404，不暴露存在性`
- 空泛注释（`// 计算`）与代码本身重复，视为无效注释

## 参数说明

| 参数 | 行为 |
|---|---|
| （无参数）或 `--all` | 检查全项目代码（脚本自动排除 node_modules/.venv/data/dist 等） |
| `<路径>` | 只检查指定文件/目录（可多个） |
| `--fix` | 检查发现注释缺陷后自动修复（**只改注释，不碰代码逻辑**） |

## 执行流程

1. **密度检查（脚本）**：运行 `node scripts/check-comments.js [路径]` 获取客观统计（注释行/代码行/密度）。退出码 1 = 存在注释不足文件，属预期信号，输出正常。
2. **语义检查（阅读）**：逐个文件阅读，检查一致性（规则 2）与小白视角（规则 3）。
3. **汇总报告**：密度数据 + 语义问题清单（文件:行号 + 问题 + 修复建议）。
4. **（可选）修复**：用户带 `--fix` 时——
   - 仅新增/修改/删除注释，**绝不改变任何代码逻辑**；
   - 修复后重跑脚本验证密度达标；
   - 若发现「注释正确但代码有 bug」：只报告，不修改（遵守 CLAUDE.md 方案决策规则）。
5. **输出报告**：按下方「报告格式」。

## 报告格式

```text
### 注释检查报告（YYYY-MM-DD HH:mm）
- 扫描文件 N 个 | 总密度 X%
- ❌ 密度不足文件：路径 | 注释 a 行 / 代码 b 行 | c% → 缺 d 行注释（估算）
- ⚠️ 密度冗余文件：路径 | …（注释过多，建议精简）
- 🔧 一致性缺陷 M 处：文件:行号 | 问题描述 | 修复建议
- 👶 小白视角缺陷 K 处：文件:行号 | 问题描述 | 正例建议
- 硬性缺失（函数无注释 / 核心代码无注释）：文件:行号 | 函数/代码段 | 建议
```

「缺 d 行注释（估算）」= 该文件代码行 × 30% − 现有注释行（≈ 达标还差多少）。

## 规则

- 涉及新技术方案（新脚本、新规则、策略调整）按 CLAUDE.md「方案决策规则」列出方案等待用户选择，严禁擅自实施。
- `--fix` 只改注释；发现代码缺陷只报告不擅自修改业务逻辑。
- 密度统计以脚本为准；脚本口径：独立注释行（`//`、`/* */`、`.vue` 模板 `<!-- -->`、Python `#`）计入，行内注释不计入（鼓励但不算密度）。
- 判定「注释冗余」时：删除无意义/重复代码本身的注释，保留解释「为什么」的注释。
- **质量优先于密度（贯穿所有规则）**：禁止为凑达标区间写多余注释；密度数字仅作参考，注释质量（信息量、一致性、小白视角）才是检查的核心。密度不足但质量合格时报告差距即可，不硬补；密度超标但注释均有信息量时不机械删行。
